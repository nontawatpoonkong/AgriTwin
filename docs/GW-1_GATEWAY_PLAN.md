# GW-1 แผนเชื่อม Gateway จริงเข้ากับ AgriTwin

> ร่างสำหรับคุยกับคนทำ Hardware (11 พ.ย. 2569) ยังไม่ได้เลือกเส้นทาง ยังไม่ได้ซื้ออุปกรณ์ และ**ยังไม่มีผลวัดระยะ**
> ระยะ 500 ม.–1 กม. ในเอกสารนี้คือเป้าหมายการทดสอบตามแผน ไม่ใช่ผลที่วัดได้
> อุปกรณ์และโปรโตคอลที่กล่าวถึงเป็นทางเลือกหรือสิ่งที่แผนเดิมเสนอ ยังไม่มีข้อใดเป็นการเลือกขั้นสุดท้าย

**ที่มา:**
- โค้ด backend บน `main` (`88c9fe5`)
- `docs/DATA_CONTRACT.md` และ `docs/ARCHITECTURE.md`
- แผน Sprint (S2 "พิสูจน์ LoRa และ Home Gateway ขั้นแรก")
- แผนจัดซื้ออุปกรณ์ 6 เฟส (หัวข้อ 2 และ 5)

**คำที่ใช้ในเอกสารนี้:**
- **Field Node** คืออุปกรณ์ในแปลงที่มีเซนเซอร์และวิทยุ LoRa
- **Gateway** คือตัวรับสัญญาณ LoRa จาก node
- **Home Server** คือเครื่องที่รัน Mosquitto, backend และ PostgreSQL
- **adapter** คือโปรแกรมที่แปลงข้อมูลจาก Gateway เป็น contract v1 แล้ว publish เข้า MQTT

## 1. สิ่งที่ backend รับได้ตอนนี้ (contract v1.0)

Gateway ไม่ต้องเรียก REST API ใด ๆ แค่ publish MQTT ตามตารางนี้

| เรื่อง | ค่าที่ต้องใช้ |
|---|---|
| Broker | Mosquitto บน Home Server พอร์ต 1883 ตอนนี้ไม่มีรหัสผ่าน จึงใช้ได้เฉพาะตอนพัฒนา ก่อนต่อจากเครื่องอื่นต้องทำ BE-3 |
| Topic | `agritwin/{env}/devices/{device_id}/telemetry` โดย `env` เป็น `dev` หรือ `prod` |
| QoS / retain | QoS 1, retain false |
| `device_id` | ตัวพิมพ์เล็ก ตัวเลข `-` `_` ยาว 2–64 ตัว (`^[a-z0-9][a-z0-9_-]{1,63}$`) และต้องตรงกับ `device_id` ใน topic |
| `schema_version` | `"1.0"` |
| `source` | `"gateway"` แอปจะไม่ติดป้าย "ข้อมูลจำลอง" ให้ข้อมูลที่มีค่านี้ |
| `ts` | เวลาที่**วัด** แบบ ISO 8601 ที่มี timezone (แนะนำ UTC `Z`) ห้ามเร็วกว่าเวลาเซิร์ฟเวอร์เกิน 5 นาที ส่วนเวลาในอดีตรับได้ |
| `message_id` | ไม่ซ้ำทั้งระบบ ยาวไม่เกิน 128 ตัว ใช้กันข้อมูลซ้ำ |
| `seq` | ไม่บังคับ เป็นเลขลำดับ frame ของ node (≥ 0) |
| `readings` | 1–32 ค่า ในข้อความเดียว `sensor_type` แต่ละชนิดห้ามซ้ำ |
| เซนเซอร์และหน่วย | `soil_moisture` `%`, `soil_temperature` `°C`, `air_temperature` `°C`, `air_humidity` `%RH`, `rainfall` `mm` (สะสมตั้งแต่ข้อความก่อน), `wind_speed` `m/s` หน่วยต้องตรงทุกตัวอักษร (`°C` คือ U+00B0 ตามด้วย C) |
| field อื่น | ไม่รับ (`extra=forbid`) ค่าอย่าง RSSI, SNR และแรงดันแบตเตอรี่จึงยังส่งไม่ได้ จนกว่าจะทำ contract v1.1 (GW-2) |

ตัวอย่าง (ค่าเป็นตัวอย่าง ไม่ใช่ผลวัด):

```json
{
  "schema_version": "1.0",
  "message_id": "node-01-b3f1-000123",
  "device_id": "node-01",
  "seq": 123,
  "ts": "2026-11-22T03:00:00Z",
  "source": "gateway",
  "readings": [
    { "sensor_type": "soil_moisture", "value": 41.2, "unit": "%" },
    { "sensor_type": "soil_temperature", "value": 27.4, "unit": "°C" }
  ]
}
```

**backend จัดการแต่ละข้อความอย่างไร:**
- **ผ่านทุกกฎ:** เก็บลงฐานข้อมูล
- **ค่าอยู่นอกช่วงที่สมเหตุสมผล:** ยังเก็บ แต่ติด `suspect`
- **`message_id` ซ้ำ:** ข้ามไป ไม่เก็บซ้ำ
- **ผิดกฎข้อใดข้อหนึ่ง:** ทั้งข้อความไปที่ `ingest_rejects` แม้ reading อื่นในข้อความเดียวกันจะถูกต้องก็ไม่ถูกเก็บ

ตรวจข้อความก่อนส่งจริงได้ด้วย `contracts/telemetry.v1.schema.json`

### เวลาที่วัด กับ เวลาที่รับ

เวลาสามแบบนี้ไม่ใช่สิ่งเดียวกัน:
- **เวลาที่วัด:** เวลาที่ node อ่านค่าจากเซนเซอร์ เป็นสิ่งที่ `ts` ใน contract v1.0 หมายถึง
- **เวลาที่ Gateway รับ:** เวลาที่ frame มาถึง Gateway ช้ากว่าเวลาที่วัดเสมอ และอาจช้ามาก ถ้า node เก็บค่าไว้ส่งทีหลัง ส่งซ้ำ หรือรอคิว
- **เวลาที่เซิร์ฟเวอร์รับ:** backend บันทึกเองอยู่แล้ว (`received_at` ของข้อความใน `telemetry_messages` และ `last_seen_at` ของอุปกรณ์) Gateway ไม่ต้องส่งมา

**NTP ทำให้นาฬิกาของ Gateway ตรง จึงได้เวลาที่ Gateway รับที่ถูกต้อง แต่ไม่ได้บอกว่า node วัดค่าเมื่อไร**

ทางที่จะได้เวลาที่วัดจริง ต้องตกลงกับคนทำ Hardware:
1. **node มีนาฬิกาที่ตั้งเวลาแล้ว:** เช่น RTC ที่ sync เวลา หรือ GPS แล้วส่งเวลาที่วัดมาใน frame
2. **node ส่ง "อายุ" ของค่า:** บอกว่าค่านี้วัดมาแล้วกี่วินาทีตอนส่ง แล้วให้ Gateway คำนวณเวลาที่วัดโดยประมาณ = เวลาที่รับ − อายุ ความแม่นขึ้นกับนาฬิกาของ node และเวลาที่ใช้ส่งผ่านอากาศ
3. **ถ้าทำไม่ได้ทั้งสองแบบ:** ใช้เวลาที่ Gateway รับแทนได้ แต่**เป็นค่าประมาณ** ต้องเขียนไว้ในเอกสารของอุปกรณ์นั้น และห้ามนำเสนอว่าเป็นเวลาที่วัดจริง
   - contract v1.0 ยังไม่มี field บอกว่า `ts` มาจากวิธีไหน ถ้าต้องการให้ระบบแยกได้ ต้องเพิ่ม field ตาม `DATA_CONTRACT.md` §6 (ตัดสินพร้อม GW-2)

ไม่ว่าจะได้ `ts` ด้วยวิธีไหน ต้องกำหนดค่าครั้งเดียวตอนรับ frame และห้ามเปลี่ยนเมื่อส่งซ้ำจากคิว

### สิ่งที่ Gateway หรือ adapter ต้องทำเอง

1. **สร้าง `message_id` ครั้งเดียวตอนรับ frame แล้วเก็บไว้กับข้อมูลในคิว** ถ้าสร้างใหม่ตอนส่งซ้ำ backend จะนับเป็นข้อมูลใหม่และเก็บซ้ำ (simulator ใช้ UUID ใหม่ทุกครั้งได้ เพราะไม่มีการส่งซ้ำ แต่ Gateway ห้ามทำแบบนั้น)
2. **`message_id` ต้องไม่ชนหลัง node reboot หรือหลัง frame counter เริ่มนับใหม่** ถ้าใช้แค่ `device_id` + `seq` หรือ `devEui` + `fCnt` ตามที่ `ARCHITECTURE.md` เสนอ ค่าใหม่หลังรีเซ็ตจะถูกทิ้งเป็น duplicate ควรเติมส่วนที่เปลี่ยนทุกครั้งที่ boot หรือ join เช่น boot id, `devAddr` หรือ id ของ uplink ที่ network server ให้มา
3. **กำหนด `ts` ครั้งเดียวตอนรับ frame** ตามหัวข้อ "เวลาที่วัด กับ เวลาที่รับ" แล้วเก็บไว้กับข้อมูลในคิว ห้ามใช้เวลาตอนส่งออกจากคิว
   - นาฬิกาของ Gateway ต้อง sync ด้วย NTP เพราะถ้าเร็วกว่าเซิร์ฟเวอร์เกิน 5 นาที ข้อความจะถูก reject
   - NTP แก้ได้แค่นาฬิกาของ Gateway ไม่ได้ยืนยันว่า node วัดเมื่อไร
4. **แปลงหน่วยและชื่อเซนเซอร์ให้ตรง catalog ก่อน publish** และไม่ส่ง reading ที่ไม่อยู่ใน catalog เพราะจะทำให้ทั้งข้อความถูก reject
5. **map ตัวระบุทางวิทยุเป็น `device_id`** (เช่น DevEUI หรือ id ที่ตั้งใน firmware) ด้วยตารางที่ตกลงกันไว้
6. **เก็บคิวเมื่อ MQTT หรือเครือข่ายหลุด แล้วส่งตามลำดับ** ตามเกณฑ์ของ S2 ให้ถือว่าส่งสำเร็จเมื่อได้ PUBACK ของ QoS 1
7. **ช่วงส่งข้อมูล:** เซิร์ฟเวอร์ถือว่า node ออฟไลน์เมื่อไม่ได้รับข้อความเกิน 180 วินาที (`DEVICE_OFFLINE_AFTER_SECONDS`) ถ้า node ส่งห่างกว่านี้ต้องปรับค่านี้

### ช่องว่างของ backend ที่เกี่ยวกับ Gateway จริง

- **MQTT ยังเปิดแบบ anonymous (BE-3):** ใครต่อ broker ได้ก็ publish ได้ ส่วน `source: "gateway"` เป็นค่าที่ผู้ส่งบอกเอง เซิร์ฟเวอร์ตรวจไม่ได้ว่ามาจาก Gateway จริง
- **เซิร์ฟเวอร์เพิ่มอุปกรณ์อัตโนมัติ:** เมื่อได้รับข้อความแรกที่ถูกต้อง ซึ่งขัดกับกติกาในหัวข้อ 2
- **ยังไม่มีที่เก็บข้อมูลสัญญาณ (GW-2):** RSSI, SNR, data rate, frame counter และแรงดันแบตเตอรี่ ที่แผนจัดซื้อต้องการ ยังไม่มีที่เก็บ

## 2. กติกาของผลิตภัณฑ์: ยืนยัน Gateway ที่มีสิทธิ์ก่อนเพิ่ม Field Node

**เซิร์ฟเวอร์ต้องยืนยันว่า Gateway มีสิทธิ์ (eligible) ก่อนยอมให้เพิ่ม Field Node ใหม่**

- **ระบบตอนนี้ยังไม่ทำตามกติกานี้** เพราะเพิ่มอุปกรณ์อัตโนมัติ ต้องมีงาน backend แยก (เสนอเป็น BE-7) ที่มี migration และ test ของตัวเอง
- **เรื่องที่ยังเปิดไว้:** ขึ้นกับเส้นทางที่จะเลือก จึงยังไม่ตัดสิน
  - **นิยามของ "มีสิทธิ์":** ลงทะเบียนไว้ก่อน, ผ่านการยืนยันตัวตน, ออนไลน์อยู่ หรือผูกกับฟาร์มหรือแปลง
  - **วิธีผูก node กับ Gateway:** ถ้าเป็น LoRaWAN มีการลงทะเบียน node และ Gateway ใน network server อยู่แล้ว ถ้าเป็น serial LoRa ต้องออกแบบเอง
  - **วิธีที่เซิร์ฟเวอร์รู้ว่าข้อความมาผ่าน Gateway ไหน:** MQTT ไม่ส่งชื่อผู้ publish ให้ผู้ subscribe จึงต้องใส่ตัวระบุ Gateway ไว้ใน topic หรือ payload และให้ ACL ของ broker บังคับว่าแต่ละบัญชีส่งได้เฉพาะในนามของตัวเอง ทั้งสองแบบเป็นการเปลี่ยน contract จึงต้องทำตาม `DATA_CONTRACT.md` §6
- **ระหว่างนี้:** simulator และ smoke test ยังเพิ่มอุปกรณ์อัตโนมัติได้ตามเดิม เพราะเป็นข้อมูลจำลอง ส่วนข้อมูลที่เป็น `source: "gateway"` ควรถูกบังคับตามกติกานี้เมื่อทำ BE-7

## 3. เปรียบเทียบสองเส้นทาง

แผนสองฉบับยังไม่ตรงกัน:
- **แผน Sprint S2:** ให้ทำ "Gateway bridge จาก serial หรือ LoRa interface ไป MQTT"
- **แผนจัดซื้อหัวข้อ 5.2:** ให้ LoRaWAN เป็นระบบหลัก และใช้ LoRa P2P เฉพาะการทดลองเฉพาะจุด

ทั้งสองเส้นทางส่งเข้า backend ด้วย contract v1 เหมือนกัน backend จึงไม่ต้องแก้

| เรื่อง | A: LoRa แบบ serial (P2P) + adapter | B: LoRaWAN + network server + adapter |
|---|---|---|
| ทางข้อมูล | เซนเซอร์ → Field Node → LoRa P2P → ตัวรับ LoRa → USB/UART → adapter บน Home Server หรือคอมพิวเตอร์เล็ก → MQTT | เซนเซอร์ → Field Node (LoRaWAN, OTAA) → LoRaWAN Gateway → เครือข่าย IP (Ethernet/Wi-Fi/4G) → network server เช่น ChirpStack → MQTT ของ network server → adapter → MQTT ของ AgriTwin |
| ฮาร์ดแวร์ที่ต้องมี | Field Node, ตัวรับ LoRa ที่ส่งข้อมูลออกทาง serial (โมดูล หรือบอร์ด MCU + วิทยุ), เครื่องที่รัน adapter และเสาย่าน 920–925 MHz | Field Node ที่รองรับ LoRaWAN, LoRaWAN Gateway ตามสเปกขั้นต่ำในแผนจัดซื้อ (AS923-1, 920–925 MHz, concentrator ≥ 8 ช่อง, packet forwarder ที่ต่อ ChirpStack ได้), backhaul แบบ IP และเสากับสาย 50 Ω |
| ซอฟต์แวร์ที่ต้องเขียนหรือดูแล | firmware ของ node และของตัวรับ, รูปแบบ frame ที่กำหนดเอง และ adapter (แปลง ตรวจ เก็บคิว publish) | payload codec, การตั้งค่า network server (region AS923-1, device profile, กุญแจ) และ adapter จาก event ของ network server เป็น contract v1 |
| ระบบที่ต้องรันเพิ่มบน Home Server | adapter อย่างเดียว | network server และระบบที่มันต้องใช้ (แผนจัดซื้ออ้างว่า ChirpStack ใช้ PostgreSQL และ MQTT broker ต้องตรวจรายการให้ครบจากเอกสารของเวอร์ชันที่จะติดตั้ง) และ adapter |
| ตัวตนและความปลอดภัยบนวิทยุ | ไม่มีในตัว ต้องออกแบบ id ของ node, การตรวจความถูกต้อง และการกันส่งซ้ำเอง | มีในมาตรฐาน: OTAA (DevEUI, JoinEUI, AppKey), การเข้ารหัส และ frame counter |
| หลาย node | ตัวรับมีช่องเดียว ข้อมูลชนกันได้เมื่อ node มากขึ้น ต้องทดสอบกับจำนวนจริง | Gateway รับได้หลายช่องพร้อมกัน และ network server กันข้อความซ้ำที่มาจากหลาย Gateway |
| ข้อมูลสัญญาณสำหรับทดสอบระยะ | ได้ ถ้า firmware ของตัวรับส่ง RSSI/SNR ออกมาทาง serial | มีใน metadata ของ uplink แยกตาม Gateway เช่น RSSI, SNR, data rate และ frame counter |
| ที่มาของ `message_id` และ `ts` | adapter สร้าง `message_id` เอง (ดูข้อ 1–2 ในหัวข้อ 1) ส่วน `ts` มาจาก frame ถ้า node ส่งเวลาที่วัดหรืออายุของค่ามา ไม่เช่นนั้นเป็นเวลาที่ Gateway รับ ซึ่งเป็นค่าประมาณ | `message_id` ใช้ id ของ uplink จาก network server (เช่น `deduplicationId` ใน ChirpStack v4 ต้องตรวจกับเวอร์ชันที่ใช้) ส่วนเวลาใน event ของ network server เป็นเวลาที่ Gateway หรือเซิร์ฟเวอร์รับ ไม่ใช่เวลาที่ node วัด ถ้าต้องการเวลาที่วัด node ต้องใส่มาใน payload |
| ความซับซ้อนในการดูแล | ฝั่งเซิร์ฟเวอร์น้อย แต่ firmware และโปรโตคอลเป็นของเราเองทั้งหมด เริ่ม bench test ได้เร็ว | ฝั่งเซิร์ฟเวอร์มากกว่า (ตั้งค่า สำรองกุญแจ อัปเดต) แต่ใช้มาตรฐานและเครื่องมือที่มีอยู่แล้ว เพิ่มจำนวน node ได้ง่ายกว่า |
| ความเสี่ยงหลัก | สัญญาณชนกันเมื่อ node เพิ่มขึ้น, ต้องดูแลโปรโตคอลเอง และถ้าย้ายไป LoRaWAN ภายหลังต้องแก้ firmware | ตั้งค่าผิดได้หลายจุด และ Gateway ต้องมีเครือข่าย IP ไปถึง Home Server ตลอดเวลา |

**สิ่งที่ต้องตรวจเหมือนกันทั้งสองเส้นทาง:**
- ย่านความถี่และกำลังส่งตามข้อกำหนด กสทช. ย่าน 920–925 MHz ที่แผนจัดซื้ออ้างไว้
- เสาที่เหมาะกับจุดติดตั้ง

### สิ่งที่ต้องพิสูจน์ในการทดสอบ 500 ม.–1 กม.

เกณฑ์ผ่านในตารางนี้มาจากแผนจัดซื้อหัวข้อ 5.5 เป็น**เกณฑ์ที่เสนอไว้สำหรับการทดสอบ** ยังไม่ได้ทดสอบ และยังไม่มีผลใด ๆ

| หัวข้อ | วิธี | เกณฑ์ผ่านที่เสนอในแผน | หลักฐาน |
|---|---|---|---|
| ข้อกำหนด | ตรวจ datasheet, ฉลาก, รุ่นย่อย และเอกสารผู้ขาย | อยู่ในย่าน 920–925 MHz AS923-1 และเอกสารครบ | ชุดเอกสาร |
| บนโต๊ะ | ส่ง uplink จาก node ทั้ง 2 ตัว อย่างน้อยตัวละ 100 ครั้ง | ถอดข้อมูลถูก และไม่มีตัวระบุหรือกุญแจซ้ำ | log และภาพหน้าจอ |
| 500 ม. | ส่ง ≥ 100 uplink ต่อ node ที่ตำแหน่งใช้งาน | PDR ≥ 95% | CSV ของ RSSI, SNR และ PDR |
| 1 กม. | ทำซ้ำบนเส้นทางและสภาพพืชจริง | PDR ≥ 90% | แผนที่จุดทดสอบ |
| ต่อเนื่อง | รัน 72 ชม. ด้วยช่วงส่งจริง | ข้อมูลถึง ≥ 95% และ reconnect ได้เอง | กราฟและ incident log |
| เวลา | เทียบเวลาของ node, Gateway และเซิร์ฟเวอร์ | คลาดเคลื่อนไม่เกิน 5 นาที | บันทึก time sync |

**ข้อจำกัดของหัวข้อ "เวลา":** เทียบนาฬิกาได้เฉพาะอุปกรณ์ที่มีนาฬิกา ถ้า node ไม่มีนาฬิกา ข้อนี้ตรวจได้แค่ Gateway กับเซิร์ฟเวอร์ ซึ่งยืนยันเวลาที่รับ แต่ยังไม่ได้ยืนยันเวลาที่วัด

**บันทึกเพิ่มทุกจุดทดสอบ** เพื่อให้ผลเทียบกันได้และอธิบายได้:
- พิกัดและระยะ
- ความสูงเสาทั้งสองฝั่ง และชนิดเสา
- ค่าวิทยุ: กำลังส่ง, SF/BW หรือ data rate และช่วงส่ง
- สภาพแวดล้อม: สิ่งกีดขวาง, แนวสายตา และสภาพอากาศ
- เวลาเริ่มและเวลาจบ
- จำนวนข้อความที่ส่ง เทียบกับจำนวนที่ถึงเซิร์ฟเวอร์ (นับจาก `seq` หรือ frame counter)

## 4. แผน integration ขั้นต่ำ (ไม่เปลี่ยน API contract)

1. **ตกลงกันก่อนเขียนโค้ด:** ประชุมกับคนทำ Hardware ตามคำถามในหัวข้อ 6 แล้วสรุปเรื่องต่อไปนี้
   - เส้นทาง A หรือ B
   - ตาราง id → `device_id`
   - ช่วงส่งข้อมูล
   - กฎการสร้าง `message_id`
   - แหล่งของเวลาที่วัด: เวลาจาก node, อายุของค่า หรือเวลาที่ Gateway รับแบบประมาณ
   - เซนเซอร์ใน phase 1
   - นิยามของ "Gateway ที่มีสิทธิ์"
2. **adapter แบบไม่มีวิทยุ (dry run, เสนอเป็น GW-4):**
   - อ่าน frame ตัวอย่างที่บันทึกจากอุปกรณ์จริง หรือ event ตัวอย่างจาก network server
   - สร้าง contract v1 ที่เป็น `source: "gateway"` แล้ว publish เข้า broker ของเครื่องพัฒนา
   - ตรวจกรณี accepted, duplicate และ rejected รวมถึงคิวตอน MQTT หลุด
3. **bench test 1–2 node:** ใช้วิทยุจริงบนโต๊ะ ตาม checklist ในหัวข้อ 5
4. **ภาคสนาม 500 ม. และ 1 กม.:** ทำตามตารางในหัวข้อ 3 และเก็บหลักฐานไว้ที่ `docs/evidence/gw-1/`
5. **ก่อนใช้งานจริง:**
   - BE-3 รหัสผ่านและ ACL ของ MQTT
   - BE-7 Gateway ที่มีสิทธิ์และการเพิ่ม node
   - GW-2 contract v1.1 สำหรับข้อมูลสัญญาณ
   - OPS-1 deploy ขึ้น Home Server

## 5. Checklist ทดสอบ integration

- [ ] ข้อความตัวอย่างจาก adapter ผ่าน `contracts/telemetry.v1.schema.json`
- [ ] ข้อความจริงถูก accepted และขึ้น Dashboard โดย**ไม่มี**ป้าย "ข้อมูลจำลอง"
- [ ] ส่งข้อความเดิมซ้ำ (`message_id` เดิม) แล้วตัวนับ `duplicate` ใน `/api/v1/health` เพิ่มขึ้น และไม่มีค่าซ้ำในกราฟ
- [ ] หยุด broker หรือ backend อย่างน้อย 5 นาทีแล้วเปิดใหม่: Gateway ส่งคิวได้ครบ, `ts` ตรงกับค่าที่กำหนดตอนรับ frame (ไม่เปลี่ยนเป็นเวลาที่ส่ง) และไม่มีค่าซ้ำ
- [ ] ถ้า node ส่งเวลาที่วัดหรืออายุของค่า: ให้ node เก็บค่าไว้ก่อนแล้วส่งทีหลัง แล้วตรวจว่า `ts` เป็นเวลาที่วัด ไม่ใช่เวลาที่รับ
- [ ] reboot node (และให้ rejoin ถ้าเป็น LoRaWAN) แล้วข้อมูลใหม่ไม่ถูกทิ้งเป็น duplicate
- [ ] หน่วยผิดหรือ `sensor_type` ที่ไม่รู้จัก ไปอยู่ใน `ingest_rejects` และไม่ขึ้น Dashboard
- [ ] ตั้งนาฬิกา Gateway ให้เร็วเกิน 5 นาที แล้วข้อความถูก reject (แสดงว่านาฬิกาของ Gateway ต้องตรง ซึ่งไม่ได้พิสูจน์เวลาที่ node วัด)
- [ ] สถานะ online/offline ตรงกับช่วงส่งจริง
- [ ] หลังทำ BE-7: node จาก Gateway ที่ไม่มีสิทธิ์ต้องไม่ถูกเพิ่ม (ตอนนี้ยังไม่ผ่าน เพราะระบบเพิ่มอุปกรณ์อัตโนมัติ)

## 6. คำถามสำหรับคนทำ Hardware

1. S2 จะเริ่มด้วยเส้นทางไหน ถ้าเริ่มด้วย LoRa P2P เพื่อ bench test ก่อน จะย้ายไป LoRaWAN ตามแผนจัดซื้อเมื่อไร
2. ตอนนี้มีอุปกรณ์อะไรแล้วบ้าง (บอร์ด, วิทยุ, เสา, Gateway) รุ่นย่อยและย่านความถี่บนฉลากคืออะไร
3. Field Node รู้เวลาที่วัดไหม (RTC ที่ตั้งเวลาแล้ว หรือ GPS) หรือส่ง "อายุ" ของค่า (วัดมาแล้วกี่วินาที) มาใน frame ได้ไหม ถ้าไม่ได้ทั้งสองแบบ `ts` จะเป็นเวลาที่ Gateway รับ ซึ่งเป็นค่าประมาณ
4. แต่ละ node ส่งข้อมูลห่างกันกี่วินาที และหลัง reboot frame counter เริ่มนับใหม่หรือไม่
5. รูปแบบ frame (เส้นทาง A) หรือ payload codec (เส้นทาง B) เป็นอย่างไร: ลำดับ byte, ชนิดข้อมูล, การคูณหรือหารค่า และหน่วย
6. node จะใช้ตัวระบุอะไร (DevEUI หรือ id ที่ตั้งเอง) และใครดูแลตาราง id → `device_id`
7. เซนเซอร์ใน phase 1 ตรงกับ 6 ชนิดใน catalog ไหม และมีค่าอื่นที่ต้องส่งหรือไม่ เช่น แรงดันแบตเตอรี่หรือสถานะ
8. ค่าวิทยุที่จะใช้ทดสอบคืออะไร (SF/BW หรือ data rate และกำลังส่ง) และใครเป็นคนตรวจข้อกำหนด กสทช.
9. Gateway จะต่อเครือข่ายแบบไหน (Ethernet, Wi-Fi หรือ 4G) และอยู่ห่าง Home Server แค่ไหน
10. เส้นทางและจุดทดสอบ 500 ม. และ 1 กม. อยู่ที่ไหน เสาสูงเท่าไร และเก็บ log อย่างไร
11. "Gateway ที่มีสิทธิ์" ควรตรวจจากอะไร (gateway EUI, serial number หรือบัญชี MQTT) และใครเป็นคนอนุมัติ
12. รอบนี้ต้องการ downlink (สั่งงาน node จากเซิร์ฟเวอร์) ไหม ถ้าไม่ต้อง จะตัดออกจากขอบเขต
